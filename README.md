# 垃圾邮件审核 · 模型版本固定 + 截止时间感知批处理

FastAPI + NumPy 的垃圾邮件审核运维控制台。网页可切换现行模型、并发提交至多 16 封邮件
（每封独立 100–1000ms 截止时间），单工作器按 **模型版本** 组批推理，逐条展示分数、分类、
模型版本与批次。

## 核心契约

| 需求 | 实现位置 |
| --- | --- |
| 排队邮件按「接单时」的版本分类 | 网关 `_run_job` 接单时快照 `active_version` 写入请求；工作器只读该字段 |
| 网页切换现行模型 | `POST /api/model` + 前端模型卡片 |
| 启动逐份读取模型 JSON，单份损坏不拖垮其他版本 | `ModelRegistry.load_dir` / `_scan` 逐文件隔离捕获异常 |
| 损坏文件在网页标出文件名与原因，并禁止切换 | `/api/models` 的 `issues` + 前端损坏卡片；切换接口对未通过校验版本返回 404 |
| 默认版损坏时显示实际启用的健康版本 | 注册表回退到健康版本并记录原因，网页顶部黄条明确提示 |
| 全部损坏才报启动错误 | `load_dir` 在零健康模型时抛 `RuntimeError`（uvicorn 退出非零） |
| 网页重试加载，半写/无效文件不进可切换列表 | `POST /api/models/reload`；只有完整通过 JSON 与模式校验的文件才入表 |
| 加载失败不影响在线分类 | 重新加载为原子快照交换；会丢失当前在线模型的扫描结果直接拒绝 |
| 加载成功后才能切换 | 切换接口只认注册表里已校验的版本 |
| 并发提交 ≤16 封、每封 100–1000ms 截止 | `SubmitIn.emails`（`max_length=16` / `ge=100, le=1000`）|
| 逐条查看分数/分类/版本/批次 | 结果表 + `GET /api/jobs/{id}` |
| 单工作器按版本组批，每批 ≤4、等待 ≤200ms | `app/batching.py` 的 `_plan` / `Worker` 默认参数 |
| 新请求立即用新版，未发批的旧请求用旧版 | 版本在接单时固定；批次按版本分区 |
| 批内不混版本 | 队列按版本分桶，`_plan` 每组批只取同一版本 |
| 最早一封快到截止时间时提前发批 | `dispatch_guard_ms`（默认 25ms）提前派发 |
| 过期请求不占后续批次 | 每个请求有独立定时器，到期即解析并从队列移除 |
| 迟到结果不得改判成功 | 批次内 `wait_for` 按各自剩余时间截断 + 完成后显式比对截止时间 |
| 同批其他邮件按各自截止时间返回 | 批内并发打分，逐条独立判定/独立完成 |

## 快速开始

### Docker Compose（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

镜像内已固定 `models/v1.json` 与 `models/v2.json` 两份不同的英文词袋线性模型，同时以可写卷
挂载 `./models`（不再用只读挂载）：值班运维修复损坏的 JSON 后可直接在网页点「重试加载」，
无需重启容器。Compose 只起 **一个** 副本、uvicorn 也只有 1 个 worker——批次调度与「现行
模型」指针都是进程内状态。

### 本地运行

```bash
python3 -m pip install -r requirements.txt
python3 scripts/build_models.py          # 重新生成模型（可选，仓库已含产物）
python3 -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

### 测试

```bash
python3 -m pip install -r requirements-dev.txt
python3 -m pytest -q                     # 38 项：调度语义 + 网关行为 + 损坏模型容错
python3 scripts/selfcheck.py             # 对运行中的服务做端到端自测（默认 :8000）
```

## 模型

两份模型都是 `bow-linear.v1` 格式（冻结词表 + IDF + 线性权重 + 偏置 + 阈值），推理只用
NumPy，网关与测试结果逐位一致。

| 版本 | 说明 | 词表 | 阈值 |
| --- | --- | --- | --- |
| `v1` | 2024 baseline，只有通用促销词 | 27 | 0.50 |
| `v2` | 2026 hardened，加入 crypto/parcel/urgency 词，权重重拟合 | 63 | 0.60 |

同一封「加密货币投资」邮件在 v1 下是 ham（0.20 左右），在 v2 下是 spam（0.87 左右），
所以版本固定能在页面上直接看出来。

## 损坏模型运维手册（值班用）

启动时注册表会**逐份**读取模型目录里的每个 `*.json`，任何一份失败都被隔离记录，不影响
其他健康版本接单。判定与处置规则：

| 情形 | 行为 |
| --- | --- |
| 单个 JSON 半写 / 非法 JSON / 模式不符（如词表与权重长度不一致、格式标识错误） | 该文件不进入可切换列表；网页「模型切换」面板出现红色损坏卡片，写明**文件名与原因**；切换到它会被拒绝（404） |
| 配置的默认版本（`DEFAULT_MODEL_VERSION`）损坏 | 自动启用排序最靠前的健康版本，网页黄条明确显示「配置的默认模型 X 不可用，实际启用健康版本 Y」 |
| 目录里所有文件都不可用，或模型目录本身缺失 | 启动直接报错退出（非零码），错误信息逐文件列出原因；不会带空模型上线 |
| 运维修好文件后 | 在网页点「重试加载」（或 `POST /api/models/reload`）重新扫描整个目录 |

重试加载的安全语义：

- 只有完整通过 JSON 解析 **和** `LinearBoWModel` 构造校验的文件才会进入新快照，半写文件
  永远不会出现在可切换列表里。
- 快照采用**原子交换**：扫描出的新模型集合整体替换旧集合，调用方要么看到完整新集合，要么
  继续看到旧集合，不存在中间态。
- 如果本次扫描会导致**当前正在线分类的模型**消失（文件被删/损坏），加载被拒绝并返回
  `unchanged_failure`，已加载模型继续接单，已接单邮件的版本固定与截止时间结算不受任何影响。
- 重新加载成功后，新恢复的版本才允许在网页切换；切换仍只影响此后接单的邮件。

> 写模型文件请使用「临时文件 + `os.replace`」原子替换（`scripts/build_models.py` 已按此
> 实现），避免被一次网页重试加载读到写了一半的内容。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 审核控制台 |
| GET | `/healthz` | 健康检查 + 现行模型 + 损坏文件列表（`model_issues` / `degraded`） |
| GET | `/api/models` | 模型列表（含来源文件、权重摘要）与损坏文件及原因 |
| POST | `/api/models/reload` | 重新扫描模型目录（运维修复后重试加载），原子交换快照 |
| POST | `/api/model` | 切换现行模型 `{"version": "v2"}`；未通过校验的版本返回 404 |
| GET | `/api/state` | 工作器指标、按版本统计、最近批次、最近任务、模型健康状态 |
| POST | `/api/jobs` | 异步提交（202），返回任务与接单进度 |
| GET | `/api/jobs/{id}` | 任务结果 |
| POST | `/api/classify` | 同步提交并等待结果（脚本/自测用） |
| GET | `/api/batches` | 最近批次记录 |
| POST | `/api/demo/interleaved` | 一键交错演示：v1 接单 → 切 v2 → 新请求 + 慢推理 |

提交体示例：

```json
{
  "label": "人工抽检",
  "emails": [
    {"text": "Congratulations! You are a winner.", "deadline_ms": 900},
    {"text": "Hi team, attached is the quarterly report.", "deadline_ms": 300,
     "submit_after_ms": 50, "simulate_latency_ms": 0}
  ]
}
```

`submit_after_ms`（0–5000）与 `simulate_latency_ms`（0–5000）是演示用：前者错峰接单，
后者模拟慢推理，用来观察「批次执行中超时 + 迟到结果丢弃」。二者只影响时点，不改变批处理
契约。

## 调度语义细节

- 队列按版本分桶；每轮只派发 **最早到期** 的那一批，避免一个慢批次吞掉另一个版本的截止时间。
- 组批规则：同版本队列满 4 封立即发批；不足 4 封时等 `min(最老入队 + 200ms, 最早截止 − 25ms)`。
  已经等满 200ms 的请求优先成批（防饿死），剩余名额用同版本 EDF 工作填充。
- 派发时同步从队列摘除并取消该请求的定时器，执行阶段由 `asyncio.wait_for(剩余时间)` 与
  完成后的显式截止检查共同判定；超时结果先到就先解析，迟到结果只做
  `late_results_discarded` 标记，**不会** 把 `timeout` 改回 `ok`。
- 批内并发打分，因此单封慢邮件不会拖住同批其他邮件；每封各自按自己的截止时间返回。

## 已知限制

- 状态全部在进程内（单工作器要求），重启会丢失进行中的任务与切换历史；没有持久化。
- 模型产物是仓库内预置的静态 JSON，没有训练流水线；网页只做「重新扫描 + 校验 + 原子换入」，
  不会在进程内重新训练。重新加载只扫描模型目录，不递归子目录，且只识别 `*.json` 后缀。
- 重试加载若会丢掉当前在线模型会被整体拒绝；要下线正在服务的版本，需先在网页把现行模型
  切到另一个健康版本，再处理文件并重新加载。
- 演示用的 `simulate_latency_ms` 通过 `asyncio.to_thread` 中的 `sleep` 模拟，结束的线程
  不会被强制中断（Python 线程无法抢占），只是其结果被丢弃。
